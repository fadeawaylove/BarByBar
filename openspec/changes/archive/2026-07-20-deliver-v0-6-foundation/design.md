## Context

BarByBar 当前以 PySide6、PyQtGraph 和本地 SQLite 为核心，已经具备逐根训练、订单线、绘图、交易复盘、后台保存、性能指标和 Windows 发布流程。现有视觉重构和第一轮性能优化大部分已经完成，但部分深层性能任务仍未收口，数据备份、恢复、导出和导入质量审查也缺少统一的用户入口。

v0.6 是后续训练、复盘和统计能力的基础里程碑。它必须保持本地优先和可携带特性，不改变交易撮合、盈亏计算和现有案例含义，也不能通过一次大规模重写制造新的稳定性风险。

## Goals / Non-Goals

**Goals:**

- 让长期工作可以仅凭仓库状态恢复，不依赖某次聊天上下文。
- 让逐根推进和常见图表交互在代表性大案例中保持可测量的响应预算。
- 为本地数据库提供可验证、可恢复的备份流程和常用交易数据导出。
- 在数据写入数据库之前提供 CSV 预览、字段确认和质量反馈。
- 收口术语、初始视窗、保存反馈以及发布前验证等基础体验。
- 将每个实现切片保持为可测试、可提交、必要时可单独发布的增量。

**Non-Goals:**

- 不增加自动播放、暗色主题、成交量副图或新的技术指标。
- 不增加账号、云同步、社区或远程服务依赖。
- 不改变订单触发、持仓、盈亏、回撤和交易复盘的业务语义。
- 不在一个提交中重写主窗口、图表或仓储层。
- 不承诺尚未通过真实大案例基准验证的性能数字。

## Decisions

### 1. 仓库文件是长期进度的唯一来源

`ROADMAP.md` 记录长期方向、当前里程碑和恢复协议；当前 OpenSpec change 的 `proposal.md`、`design.md`、`specs/` 和 `tasks.md` 记录范围、约束和任务状态。聊天只用于协作，不作为完成状态来源。

采用这一方案而不是单独维护外部待办，是因为仓库文件能够与代码版本、评审和发布标签一起演进，也能在新对话或新机器上恢复。

### 2. v0.6 按可发布的纵向切片实施

实施顺序为：基线与恢复协议、推进快路径、数据备份与导出、导入质量审查、基础体验、发布门槛。每个切片都包含用户可见行为、测试和验证记录；不等待整个里程碑完成才提交。

这比按“先重构所有架构，再补界面”的方式风险更低，并允许在中途发布必要的修复版本。

### 3. 性能优化扩展现有失效标记和指标体系

继续使用现有图表层失效标记、延迟刷新、性能指标和异步任务协调器。逐根推进快路径增加工作台区域级状态比较：订单线、持仓、统计、价格输入、绘图控制和案例标题只在相关状态变化时更新。

不引入新的 UI 框架或通用响应式状态库，因为迁移成本高且会扩大回归范围。深层优化依次考虑 K 线图片分块缓存、指标增量计算和可交互对象空间预筛选，并以基准结果决定是否继续。

### 4. 备份使用 SQLite 一致性快照，恢复在下次启动前完成

创建备份时使用 SQLite 支持的一致性备份方式写入临时文件，验证可打开后再原子重命名为最终备份，避免直接复制正在写入的数据库。

恢复时先验证所选文件的 SQLite 格式和必要表结构，再将其登记为待恢复文件。应用在下一次启动、创建 Repository 之前完成当前数据库备份和原子替换。这样避免在大量窗口和后台任务仍引用旧连接时热替换数据库。

备份和恢复不改变数据库模式；任何失败都必须保留原数据库和已存在备份。

### 5. 导出以稳定的用户字段为边界

v0.6 首先支持交易记录和案例摘要导出为 UTF-8 CSV/JSON。导出模型由领域对象或专用视图模型生成，不直接暴露数据库内部列名，避免后续迁移破坏导出格式。

### 6. CSV 审查与持久化分为两个阶段

新增纯分析阶段读取表头、样例行和必要统计，输出字段映射建议、可导入数量、阻断错误和非阻断警告。只有用户确认映射和审查结果后，才调用现有导入持久化路径。

阻断问题包括缺少必要字段、无法解析的时间或 OHLC 数值、无有效数据；重复时间、时间倒序、异常时间间隔和异常 OHLC 关系必须在审查中明确展示，并根据严重程度阻断或警告。

### 7. 基础体验继续沿用现有专业浅色主题

v0.6 只修正信息层级和一致性：中文术语、适应已揭示数据量的初始视窗、明确保存状态、高频操作反馈和关键空状态。所有样式继续通过现有主题角色实现，不增加一次性的颜色和装饰。

### 8. 发布门槛是任务完成的一部分

每个切片至少运行聚焦测试；里程碑完成前运行完整测试、代表性性能基准、关键状态截图、安装包冒烟和 Release 产物验证。任务清单只有在验证证据存在时才能勾选完成。

## Risks / Trade-offs

- [里程碑范围较大] → 按纵向切片提交，任务清单明确依赖关系，并允许中途发布补丁版本。
- [恢复操作可能造成数据丢失] → 恢复前自动备份当前数据库，验证来源文件，使用启动前原子替换，失败时保持原文件。
- [导入审查可能增加操作步骤] → 默认提供自动映射和简明摘要，只有存在问题时展开详细信息。
- [状态比较可能造成界面遗漏更新] → 为每个跳过更新的区域增加状态转换测试，并保留完整刷新路径用于加载和恢复。
- [性能基准受机器环境影响] → 记录数据规模和相对变化，使用预算作为警告门槛而非正确性断言。
- [长期路线与实际需求偏离] → 每个小版本开始前复核路线图，只调整未开始的里程碑，不悄悄扩大当前范围。

## Migration Plan

1. 先提交路线图、OpenSpec 工件和基线验证，不改变运行行为。
2. 逐个交付性能、数据安全、导入审查和基础体验切片。
3. 数据安全功能不修改现有数据库模式；首次启用时创建专用备份和待恢复目录。
4. 每个切片保留独立提交，出现回归时可以按切片回退，而不回退用户数据库。
5. v0.6 完成后归档 OpenSpec change，将路线图当前里程碑更新为 v0.7。

## Open Questions

- 交易导出的第一版是否同时需要人类可读 CSV 和完整可交换 JSON，还是分两个切片交付。
- 导入质量检查中异常时间间隔的默认阈值是否应按数据周期自动推导并允许用户忽略。
- 恢复完成后是否自动重启应用，或先采用更安全、实现更简单的“退出后重新打开”提示。
